# 换一课技能互换 MVP 产品定义

## 1. 产品定位

“换一课”是一个双向技能交换平台：用户发布“我能教”和“我想学”，系统按技能、方向、时间与互惠意愿进行匹配，双方通过申请、确认并完成一次技能互换。

MVP 只验证一个核心假设：**当双方明确知道彼此能提供什么、想获得什么，并能低成本完成一次确认时，用户愿意发起并完成技能互换。**

### 目标用户

- 有一项可教技能，同时希望学习另一项技能的个人用户。
- 典型场景：英语口语换吉他、Excel 换摄影、产品设计换数据分析。
- MVP 不面向机构、付费课程、复杂社群或职业认证场景。

### 成功指标

- 新用户能在 3 分钟内完成一条“我能教”和一条“我想学”。
- 用户能在 2 分钟内理解一个匹配结果并发起申请。
- 从申请到接受、完成、评价形成可追踪闭环。
- 演示过程中至少完成 1 次双向匹配和 1 次完整交易状态流转。

## 2. MVP 范围

### 必须支持

1. 创建个人资料：昵称、城市/时区、可用时间、简介。
2. 发布“我能教”：技能名称、熟练度、可教内容、可用时间、期望交换技能。
3. 发布“我想学”：技能名称、目标、当前水平、期望时间、可提供的交换技能。
4. 双向匹配：A 的“我能教”匹配 B 的“我想学”，同时 B 的“我能教”匹配 A 的“我想学”。
5. 匹配结果解释：显示匹配的教与学技能、时间重合、匹配分或匹配原因。
6. 申请：申请人选择一条匹配，填写简短留言和建议时间。
7. 接受、拒绝、取消：被申请人可接受或拒绝；申请人在对方处理前可取消。
8. 完成：双方确认交换已完成，记录完成时间和交换主题。
9. 评价：双方分别提交 1-5 星和一句话反馈；评价后展示在已完成记录中。
10. 状态列表：待处理、已接受、进行中、已完成、已拒绝、已取消。

### 明确不做

- 支付、退款、平台抽成、优惠券和商业化。
- 实时聊天、视频会议、文件传输和日历自动同步。
- 实名认证、证书验证、背景调查和内容审核后台。
- 推荐算法训练、复杂权重配置、无限滚动信息流。
- 多人课程、群组交换、机构账号、申诉仲裁和信用分体系。
- 跨语言自动翻译、AI 自动生成课程和自动排课。

## 3. 核心对象与状态

### 核心对象

- **用户**：拥有个人资料，以及“我能教”和“我想学”条目。
- **技能条目**：类型为 `teach` 或 `learn`，包含技能、目标、时间和交换诉求。
- **匹配**：两名用户之间的双向技能关系，必须能解释双方的交换价值。
- **申请**：基于某个匹配发起的交换请求。
- **评价**：交换完成后由双方各提交一次。

### 申请状态机

`待处理 -> 已接受 -> 进行中 -> 已完成`

可从 `待处理` 转为 `已拒绝` 或 `已取消`；已接受后可转为 `已取消`；已完成后不可再取消。评价仅允许发生在 `已完成` 状态，且每位参与者每次交换只能评价一次。

### 双向匹配规则

匹配同时满足以下条件：

1. A 的可教技能与 B 的想学技能相符。
2. B 的可教技能与 A 的想学技能相符。
3. 双方至少有一个可用时间段重合，或双方明确选择“时间待协商”。
4. 双方的交换目标不是同一条单向需求的重复发布。

MVP 匹配分可采用透明规则：技能相符 60 分、时间重合 25 分、目标/水平相近 15 分。低于 60 分不展示为“推荐匹配”，但可以通过搜索或直接查看个人条目发现。分数不是信誉分，不影响接受申请。

## 4. 用户旅程

### 旅程 A：发布并找到匹配

1. 用户进入首页，看到自己的“我能教”和“我想学”状态。
2. 用户创建“我能教”：例如“英语口语，能帮助初级学习者进行日常对话”。
3. 用户创建“我想学”：例如“吉他入门，希望学会 3 首完整歌曲”。
4. 系统展示匹配列表，每条明确写出“你教英语 ↔ 对方学英语；对方教吉他 ↔ 你学吉他”。
5. 用户打开匹配详情，查看对方简介、技能条目、时间和匹配原因。

### 旅程 B：申请到接受

1. 用户点击“发起互换申请”。
2. 填写留言和建议时间，例如“我可以周六 14:00 教 30 分钟英语，也想学习吉他和弦”。
3. 对方在申请列表看到匹配摘要、留言和建议时间。
4. 对方选择“接受”或“拒绝”；申请方在处理前可“取消”。
5. 接受后双方进入“进行中”，看到本次交换的技能、时间和下一步行动。

### 旅程 C：完成与评价

1. 双方完成约定的一次交换。
2. 任一方点击“标记完成”；另一方确认后，状态变为“已完成”。
3. 双方分别提交星级和一句话评价。
4. 完成记录展示交换主题、完成时间和评价结果。

## 5. 页面与功能边界

### MVP 页面

- 首页/我的：个人资料、我的技能条目、待处理申请、进行中与历史记录。
- 发布技能：分别创建“我能教”和“我想学”。
- 匹配列表：推荐匹配、匹配原因、筛选技能和时间。
- 匹配详情：双方资料、双向关系、发起申请。
- 申请详情：留言、时间、状态动作。
- 完成/评价：确认完成、提交评价、查看历史。

### 必须可用的反馈

- 表单校验：技能、目标、时间、留言不能为空。
- 每次状态变化给出明确成功或失败反馈。
- 空状态说明下一步动作，例如“先发布一条我想学”。
- 防重复提交：已处理申请不可再次接受/拒绝，已评价记录不可重复评价。

## 6. 真实服务与演示边界

### 真实服务边界

真实版本至少需要：

- 持久化用户、技能条目、匹配、申请、完成记录和评价。
- 服务端校验状态机、参与者权限和重复操作。
- 登录或可替代的用户身份机制，确保 A 不能操作 B 的申请。
- 服务端执行匹配规则，并返回可解释的匹配原因。
- 操作时间、操作者和状态变更结果可追踪。

真实版本暂不承诺：支付安全、线下人身安全、技能真实性或交易纠纷裁决；产品需在提交申请和完成页明确“平台仅提供撮合，双方自行确认地点、方式与安全安排”。

### 30 分钟演示替身

允许使用本地内存或固定种子数据完成演示，但必须满足：

- 演示数据明确标注为“示例用户/示例匹配”，不得伪装成真实用户。
- 预置至少 2 个互相匹配的用户，覆盖教英语/学吉他等双向关系。
- 所有主流程按钮真实改变前端状态，不能只展示静态页面。
- 刷新后数据可丢失可以接受，但界面需明确“演示模式，数据仅保存在当前会话”。
- 不接入支付、短信、邮件、实时通信或第三方账号，避免把演示替身误认为真实服务。

## 7. 验收标准

### P0：30 分钟首版必须通过

- [ ] 能创建或切换至少 2 个示例用户。
- [ ] 每个用户能发布“我能教”和“我想学”。
- [ ] 系统只把双方互相满足的需求展示为匹配，并显示匹配原因。
- [ ] 匹配详情能发起申请，申请包含留言和建议时间。
- [ ] 接收方能接受、拒绝；发起方在处理前能取消。
- [ ] 接受后能进入进行中，并完成双方确认流程。
- [ ] 完成后双方都能各评价一次，重复评价被阻止。
- [ ] 状态在首页、申请详情和历史记录中保持一致。
- [ ] 缺少必填项、重复点击和非法状态操作有可见错误提示。
- [ ] 演示可以从发布技能开始，在 5 分钟内走完一条完整闭环。

### P1：48 小时迭代必须通过

- [ ] 使用真实持久化数据，刷新或重新登录后状态不丢失。
- [ ] 有真实身份隔离和服务端权限校验。
- [ ] 匹配规则在服务端执行，结果可通过测试覆盖。
- [ ] 支持时间段重合判断，并在无重合时给出明确原因。
- [ ] 申请状态机有单元测试，覆盖接受、拒绝、取消、完成、重复操作和越权操作。
- [ ] 关键页面具备移动端可用布局、加载态、空状态和错误态。
- [ ] 评价能在历史记录中展示，且双方评价互不覆盖。
- [ ] 记录基本事件日志：发布、匹配、申请、状态变化、完成、评价。
- [ ] 有最小隐私与安全提示，不收集非必要敏感信息。

## 8. 30 分钟首版实施顺序

### 0-5 分钟：数据与壳

- 建立页面路由或单页视图。
- 准备 2 个示例用户、4 条技能条目、1 条可解释的双向匹配。
- 建立申请状态枚举和当前用户切换。

### 5-12 分钟：发布我能教/想学

- 完成两个发布表单。
- 将提交内容写入当前会话数据。
- 在我的页面展示条目和空状态。

### 12-18 分钟：匹配与申请

- 实现双向规则筛选。
- 展示匹配详情和匹配原因。
- 实现申请表单、提交和待处理列表。

### 18-25 分钟：接受/拒绝/取消/完成

- 实现状态按钮和状态保护。
- 接受后进入进行中，完成后进入已完成。
- 在各相关页面同步状态。

### 25-30 分钟：评价与验收走查

- 添加星级和文字评价。
- 走一遍完整演示路径。
- 修复阻塞主流程的交互问题，并记录未实现项。

## 9. 48 小时迭代计划

### 第 1 阶段：0-8 小时，闭环固化

- 将内存模型替换为真实数据模型和 API。
- 服务端实现匹配、申请状态机和权限检查。
- 增加关键路径单元测试与接口测试。

### 第 2 阶段：8-24 小时，真实可用性

- 完善登录、身份隔离、持久化和错误处理。
- 加入时间段匹配、筛选和匹配原因。
- 补齐移动端布局、加载态、空状态和重复操作保护。

### 第 3 阶段：24-36 小时，可信度与反馈

- 增加基础事件日志和管理查看能力。
- 增加评价展示、举报入口占位和安全提示。
- 用 3-5 名测试用户完成可用性走查，记录申请转化和中断点。

### 第 4 阶段：36-48 小时，发布准备

- 修复 P0/P1 缺陷，补充部署配置和种子数据脚本。
- 验证刷新、重新登录、越权、重复提交和异常网络场景。
- 输出演示脚本、已知限制和下一阶段候选需求。

## 10. 发布判定与后续方向

### 可以对外演示

当 P0 全部通过，且主流程可在 5 分钟内完整走通，即可作为 MVP 演示版。演示时必须说明当前是否为演示模式、数据是否持久化，以及平台不负责线下安全与技能真实性。

### 可以小范围真实试用

只有当 P1 全部通过、身份和数据持久化可用、关键状态机测试通过，并完成至少一次真实用户走查后，才可邀请小范围用户使用。

### 48 小时后暂不承诺

规模化推荐、聊天和日历集成、支付托管、身份认证、信用体系、内容审核和纠纷处理都不属于本轮交付承诺，应基于真实使用数据再决定优先级。
